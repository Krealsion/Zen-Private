Colors
  Colors need a whole new system. I do not like how light_paint is the class that sets up the colors, and are incredibly difficult to read
  I think we should just hav a color scheme that can be created or accessed in certain ways
  Perhaps colors are a sense that can be read from, or perhaps they instantiate their own that can't be overriden
  Perhaps we simply look for Colors that are exposed and use those as the hooks for setting colors with a theme, regardless of if that color was in a theme before
    This could likely fail if a large theme has colors for weaves that no longer exist, and maybe a config for if it should fail gracefully on those slots and continue on others, or fail completely, resolving each one beforehand
  I also would *like* one of these shared repositories to be for shared use cases. For instance, background color. If we had a helper like that, where colors where the name was the use case, then many things could reliably pull from the same pool and look similar without knowing about eachother or being set seperately. 
  So overall, `light_paint.cpp` should be more just the "Painter" functionality, no colors known, passed in for each action like drawing an ellipse or rectangle, and then the panes should have rich access to ways to color their panes exactly how they want, or via a shared pool. This is likely the same shared pool concept we will use for things like fonts and text sizes.
  I also think the data should be stored in JSON, so we can edit themes and load them without any compiling necessary.

The Window, keys and presses
  1. This is kind of personal preference as long as it works the same either way. I personally think panes should get first dibs, with an elevating consumption policy. If a press goes to a pane and isn't consumed, then it goes up to workshop. Or panes could maybe opt in/out to workshop key defaults, which lets' their own key listener fall back to workshops at the end if it's not consumed. This also let's panes override workshops globals, for things like the neovim setup, rather than workshop getting first dips, and panes having to work around them.
  2. One shape makes sense in theory, but a hotkey that does the same action as a button is not the same as clicking that button. A pane may need to know the click regardless if they want to do some kind of sparkles where you click. So the real shape would be a single shape that also carries the source inside of it, which includes the mouse position if it's a click, or just the information it was a keypress with no additional information. Can maybe also let this carry if it was a spoofed click by an agent, which could be cool for some visualizations of agent actions.
  3. Your lean, leave it. Someone could likely build out a migration pattern already, albeit likely very specific to a case. We shouldn't need to build out a generic one.
  4. If by "key" you mean an id representing a button that can be pressed, I agree. If you mean a "hotkey" then no, we shouldn't force every clickable to have a hotkey. If it's the former, I would also be curious as to why we only can click buttons that have messages attached, as that sounds like it'd be hard to detect specifically. If it's the latter, I would almost prefer if it was just an agent tool that asked for an action and resolved how to do that action, be it a press or a key if that is the issue. More information required before a final decision.
  5. I do not really understand this one.
  6. I also do not understand this one.
  7. See answer 1. I think the pane itself should own the hotkey, including the global row it registers, as the same key, and have the registered action globally open it or select it if open, but have it's internal handling of the key close itself.
  8. Unsure how this plays out, given other decisions so far.

Layout and Docks
  1. Docks cover the room. Anchors will be how panes react dynamically. Moving panes that are not authored to be moved yet is a recipe for undefined/unexpected behavior. Only authors can determine what really should move. A dock could simply be a popup someone needs for a moment, but now their work is getting rearranged, and maybe altering where they intended to drag and drop to from that docked pane.
  2. Need more specifics to answer this one.
  3. For an example, if a pane wants to dock on the right edge, the entire right edge bar would be preserved, so the height of the pane would not change when docked or opened. The dock area would take up space as if it was a scrollbar regardless if it was opened or closed, and have a vertically centered arrow pointing left when closed, or right when opened.
