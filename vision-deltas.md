## 1. Lifecycle

```text
RAW       source capture; not authority
SEEDED    coherent candidate; not accepted work
INCORPORATED
          consequence placed into a current authority
REJECTED  deliberately not pursued under current understanding
SUPERSEDED
          replaced by a later decision; retained here only when the contrast still matters
```

An implementation still requires an authorized phase prompt. A raw or seeded idea cannot override
current source, repository law, the Strategic Map, or a Goal Map.

## 2. Incorporated strategic decisions

### VD-01 — Power is made honest, not reserved

**Status:** INCORPORATED  
**Destinations:** Strategic Map purpose/invariants; public vision/orientation

Safety enables fearless creation. No Zen-supplied participant, tool, UI, debugger, or policy
delegate is privileged merely because it belongs to the system.

### VD-02 — Consumer pressure, not demo pressure, earns mechanisms

**Status:** INCORPORATED  
**Destinations:** Strategic Map horizon firewall; Workshop phase rules

A real consumer must demonstrate a truth the current surface cannot express honestly. Horizons may
define completeness; they do not authorize framework work or dream-demo special cases.

### VD-03 — Intent, resolution, presentation, and history are separate truths

**Status:** INCORPORATED  
**Destinations:** Strategic Map laws; Workshop ownership model

Persist authored intent. Resolve current availability, geometry, capability, and presentation from
live owners. Recorder, Logger, current state, and final snapshots answer different questions and
must not be collapsed into one record.

### VD-04 — The actor remains the actor

**Status:** INCORPORATED  
**Destinations:** Strategic Map; Loom authority law; Workshop boundary

The Kernel/Switchboard enforces; a bounded Weaver may decide delegated LiveAuthority; a Session
performs its own action under its own identity. Presentation may author a request for that Session
without inheriting its grant.

### VD-05 — Different questions need different owners and lifetimes

**Status:** INCORPORATED  
**Destinations:** Strategic Map law; operator/message/Workshop routed law

Composable, accepted, semantically declared, currently applicable, draft-appropriate, authorized,
delivered, and successful are not one `valid` or `available` flag. Discovery and enforcement should
spend the same underlying truth where they answer the same question.

### VD-06 — Composition consumes existing power

**Status:** INCORPORATED  
**Destinations:** Strategic Map; operator architecture; Workshop long path

Native primitives introduce only power Zen cannot already express. Composites reuse current
operators. Generated code may carry schemas, adapters, ABI glue, registration, and build ceremony;
authored code carries meaning. Let the language compiler parse the language.

### VD-07 — Identity survives; implementation is resolved at spend

**Status:** INCORPORATED  
**Destinations:** Strategic Map identity/provenance law; provider/operator/pane architecture

Durable intent retains stable provider, pane, operator, recipe, and artifact identity. It does not
retain a WeaveId, loaded image, provider-local index, native function pointer, path, or hash as
semantic identity. Execution resolves and holds the current provider; provenance names the concrete
incarnation that answered.

### VD-08 — Build intent and load intent are separate project truths

**Status:** INCORPORATED  
**Destinations:** Strategic Map; Workshop Goal Map; Builder/realization law

What the project builds and how an artifact participates are authored separately and join by
artifact stem. Explicit lists carry authority; directory scans do not. A process exit, artifact
existence, realization eligibility, and live replacement are separate facts.

### VD-09 — Workshop owns composition, not provider meaning

**Status:** INCORPORATED  
**Destinations:** Workshop Goal Map and routed pane law

A pane identity is not a weave identity. Provider route, pane kind, PaneRef, mounted instance,
and presentation are different identities, including when a participating weave presents the pane (VD-19). Workshop owns catalog resolution, room, bounds, clipping, ordering, paint/hit,
recovery, and retained bounded content. A provider owns the meaning it publishes inside the grant.

### VD-10 — A project desk is durable without becoming the document

**Status:** INCORPORATED  
**Destinations:** Workshop ownership/current capability

Named setup, last session, user preferences, window placement, and object document remain separate
stores. Per-user config and state follow the maker; project files follow the project. Restoring the
desk does not silently choose the document.

### VD-11 — Context remembers a subject, not its existence

**Status:** INCORPORATED  
**Destinations:** Workshop law

Pointing names a subject for one request; it does not become selection or focus. Context records a
stable identity, and the owner judges existence and applicability again at spend. A menu references
the one action truth and never becomes a second policy/command system.

### VD-12 — Standing conditions are not event notices

**Status:** INCORPORATED  
**Destinations:** Workshop Attention law

An event report was true at one moment and may be replaced by the next report. A standing condition
must remain visible until its owner says it is no longer true. Hiding a condition changes
presentation only and is scoped to the exact statement hidden.

### VD-13 — The editor owns source opening

**Status:** INCORPORATED (landed as EDIT-1, 2026-09)  
**Destinations:** Workshop Goal Map §6; `Zengine/agents/workshop/project.md`, `editor.md`

Builder is one source referrer, not source authority. The host captures project-root truth; Project
Files and Builder resolve paths; every path enters one normalized Editor-owned door that preserves
dirty refusal and representation law. One document remains the product truth.

### VD-14 — Rigor must be cheap to carry

**Status:** INCORPORATED  
**Destinations:** Strategic Map process doctrine; current handoffs

Prompt Contract v1 single-sources stop conditions, references standing rules, states the baseline,
uses compact QR lanes for bounded work, preflights large unresearched production prompts, and splits
substantial decision reports from exhaustive evidence. `REPOSITORIES.md` is a stable registry, not a
moving accepted-HEAD board. Current law is rewritten by subject; chronicles stay in reports/history.

### VD-15 — Hand-offs carry state and lessons, never direction

**Status:** INCORPORATED (2026-09-05)  
**Destinations:** `private/handoffs/Zen-FCO-v2.md` (first read); `zen-orientation.md` §8

Two September Vision sessions proposed and drove an interpreted maker-authored weave as "Phase 2"
through their hand-offs; no live authority had selected it, and the next Vision inherited the frame.
Direction lives in the maps. A hand-off that proposes a direction is a candidate for this index, not
a phase. Every architectural claim a Vision makes carries `file:line` at a named head; "I have not
read X" is the only honest form of not knowing.

### VD-16 — Zengine is an IDE for real C++ on Loom; interpreted execution is a pressure point

**Status:** INCORPORATED (2026-09-05)  
**Destinations:** Strategic Map §6; Workshop Goal Map §2, §7; `private/goals/two-forms.md` (horizon)

The founder's statement of what Zengine is for: essentially an IDE that reloads code in place with
a seamless handoff, partial compilation of the specific part, swapped in — quick and easy, not
instant and braindead. Interpreted execution is useful only where code must run with no
compilation; the `maker/` package (Zengine PR #10, zero Loom changes, first-class state schema,
MIG-0 reused) is PAUSED as a pressure point, not removed. Its lasting value may be its definition
format as the schema builder's document before a `ZEN_SHAPE` is generated.

### VD-17 — Nothing is upgraded silently; the same-shape rung comes first

**Status:** INCORPORATED (2026-09-05–06)  
**Destinations:** Workshop Goal Map §2, §7; pressure P-WORK-07, P-WORK-15; Zengine `agents/realization.md`, `authoring.md`

A rebuilt same-shape artifact reloads in place through Loom's own door, state kept; the new image is
not the default load until the maker promotes it, with revert to the previous image. Load-after-build
is one action with one button in two states; no confirmation dialog — the press is the action. A
changed shape is refused in a maker's words and is the next rung, through Loom's prepared
replacement and authored handoff. Detection never becomes authority: picking a buildable authors a
recipe row; "load it" authors a plan row with a role the maker types; a project catalog and plan at
the project root are project truth found at launch, and the shipped defaults beside the executable
are installation truth no maker gesture writes.

### VD-18 — Generated C++ is the default form; the definition is for live concept-testing

**Status:** INCORPORATED (2026-09-06, the founder's word)  
**Destinations:** Strategic Map §6; Workshop Goal Map §7; `private/goals/two-forms.md` (horizon)

The schema builder authors source — the `ZEN_SHAPE` and the weave's boilerplate, written into
C++ the maker holds — not a definition document. `maker/`'s definition is for live, fast testing
of a concept and, later, the blueprint durable code is generated from (two-forms); saved as the
default it is one more layer between a maker, their intent and the machine, and a person who can
code should not meet it by default. `maker/` stays paused. The emitter that turns (name, version,
fields) into a `ZEN_SHAPE` is one function whether a form feeds it now or a definition feeds it
later — a seam to name, not to build. At this decision the founder chose research into a new
weave authored from Workshop (`prompts/new-weave-research.md`). Later sequencing lives in the
Workshop Goal Map; the research choice is not a standing production authorization.

### VD-19 — Workshop's panes are participating weaves; the host is room, focus, realization, roots

**Status:** INCORPORATED (2026-09-06, the founder's word)  
**Destinations:** Strategic Map §3, §6; Workshop Goal Map §1, §4, §7, §11; `private/handoffs/Zen-FCO-v2.md`; pressure P-WORK-03, P-WORK-07, P-WORK-19

The founder, on reading `keymap.hpp` (144 rows in one catalog) and `screen.hpp` (151 KB): Loom
supports healthy development only if used correctly, and the built-in panes were written as C++
inside the host instead of as weaves — that is the debt. Direction: every pane a maker sees inside
Workshop is a participating weave, loaded from the plan, interacting only by messages; the host
keeps room, clipping, front order and the setup file, focus routing, the keymap's assembly and
collision law, the realization owner, the Kernel/Manager/control door and the user roots. Split
until a piece is too small to be useful; then it is an operator, and operators compose. The pane
protocol extends only where a migrating built-in demonstrates one missing contract — P-WORK-03's
trigger, fired on purpose — never into a plugin framework. Consequences: the keymap becomes
registration from a pane's declared actions, assembled at load under the collision law (a
constexpr split of `kActionCatalog` is superseded — do not do it); `Session`/`screen.hpp` dissolve
as panes leave; a pane replaced by a differently-shaped one (a vim Editor) is prepared replacement
with an authored migration, the document as the migration's currency — P-WORK-07's second rung
with a case. Migration order is by smallest protocol delta, measured by a research phase before
any migration; the first pane weaves are hand-written C++ as Introspection was; the new-weave
production phase waits behind them, its research standing.

### VD-20 — Send fate, then obligation — two Loom changes, in that order

**Status:** INCORPORATED (2026-09-06, the founder's word; Loom-tier)  
**Destinations:** Strategic Map §4, §6; pressure P-LOOM-02, P-WORK-14; Loom (a later phase, read whole)

Fate: a sender hears, as a later delivery, that its send was refused at dispatch
(`CapabilityDenied`, `NotAccepted`, `GateRefused`, `NoSuchTarget`) — keeping PR-01's rule that a
sealed candidate stays indistinguishable from nothing. Obligation: an ask may be answered
incompletely, with progress, before a closing answer; the founder's handle is that an answer is
authorized by the ask, not by the answerer's send rules, so progress rides it. Consumers that fire
the board's trigger: the Builder's progress, the Weaver's pending approval, the realization
owner's waiting row. Retires "author it per domain" for these consumers. Fate first: VD-21's
approval flow cannot start from a denial the sender never hears. The `--log` reader (P-WORK-14)
lands before the first shape collision, so it arrives as a sentence.

### VD-21 — Authority: the plan row asks; the host's policy decides; the Weaver is the hand

**Status:** INCORPORATED (2026-09-06, the founder's word)  
**Destinations:** Strategic Map §3, §6, §8; Workshop Goal Map §4, §11; `private/handoffs/Zen-FCO-v2.md`; pressure P-WORK-15, P-WORK-18

Today every artifact the Kernel loads gets `allow_any()` (`Loom/src/kernel/kernel.cpp:992-998`;
the four-argument overload takes a grant). The founder: the plan row is a request at best —
editing a text file gives no power. The host's policy mints the loaded tier's baseline from the
request (GATE-05: a baseline never changes; delegated authority moves); the Weaver is the
middleman, set to auto-approve what the maker allows, free to refuse. A refused weave must know
(VD-20) and may declare itself broken or request its own unload; none of the requests need be
granted; a snake game may ask for load or unload authority as a one-time request. One-shot
authority is not claimed by Loom today (known-seams: "allow once is not claimed"; a policy that
needs it brokers the action) — a horizon the substrate earns, noted here, not built. The approval
modal is the lever (P-WORK-15's general modal gains its second consumer); the Weaver's seat in
Workshop — an ordinary participant with approve/refuse/revoke/describe, TERM-0's shape — is the
hand. `allow_any()` retires as the loaded-tier default when the row carries a request and the seat
exists. Authority dependency order: fate (VD-20) → the row carries a request → seat and modal →
migrations under real grants. The founder later advanced separation ahead of this authority work;
VD-25 is the current sequencing decision. In-process, what this governs is what a pane may say — legibility of
composition, not defense against a hostile image.

### VD-22 — A pane's keys act only after the maker has pointed at the pane

**Status:** INCORPORATED (2026-09-07, the founder's word)  
**Destinations:** Workshop Goal Map §4; pressure P-WORK-03; `prompts/builder-pane-weave.md`

Command-mode keys that act on a pane's subject retire with the pane: `b` builds only after the
maker has pressed into the Builder. Nothing does something "by default" from anywhere. Richer
routes — buttons, hovering a pane to hand it the keys, Workshop mapping a key to a weave's action
itself ("weaves relying on other weaves is not a bad thing") — are later UX with many options,
none of them a default at that decision. Builder was next then; the Workshop Goal Map owns
the current migration status and sequence.

### VD-23 — The reserved side column retires; Info is an ordinary pane

**Status:** INCORPORATED (2026-09-08, the founder's word)  
**Destinations:** Workshop Goal Map §7; pressure P-WORK-03; `prompts/pane-weaves-remaining.md` (CONTINUE)

The Info migration stopped on a fact: a loaded pane is an overlay-stack pane, and the side
column is reserved by geometry (`room_w = w - kPanelCols - kPanelGap`, unconditionally), so
retiring the built-in leaves a dead 30-column strip nothing may occupy. The founder chose the
end state VD-19 argues for: the reservation goes, room is the whole screen, Info is an arranged
pane like the browser and the Builder, and a shipped default setup opens it at the right edge so
a fresh session looks as it did while the strip beneath is ordinary room a maker can take back.
Refused: a placement field on `PaneOffered` (the first sentence in which a pane says where it
goes — the "wants keys" crack by another name) and keeping the column for one office by rule.
A long-standing wish of the founder's — Info as a pane — that the arc reached on its own. The
order at this decision was geometry, then Info's second stage, then Editor. VD-24 subsequently
added Terminal; the Workshop Goal Map owns current status and VD-25 owns the revised sequence.

### VD-24 — The Terminal is a pane too; the founder's theory of the arc

**Status:** INCORPORATED (2026-09-08, the founder's word)  
**Destinations:** Workshop Goal Map §7; pressure P-WORK-03; `prompts/pane-weaves-remaining.md` (CONTINUE)

The geometry PR (Zengine PR #21) retired the reservation and exposed that the terminal overlay had
been doing a second job — it could not erase what stood at the right column — and that no mechanism
for that job survives without the screen knowing a pane is furniture. Offered chrome, paint order
or a ceiling, the founder chose none: the Terminal becomes its own pane weave, and wears a pane's
boundary by construction. The stays-host list shrinks to Layouts, the Pane Manager and the maker
pane. His theory, stated: "Panes becoming individual participants via a weave will result in more
extensible and modular architecture that will reveal more ideal code patterns" — and the arc is
already the evidence. The Terminal's delta was never measured (research E5 left it host); the
migration measures first and stops if the participant it reads by pointer today needs a Loom door
(the Loom fence; VD-20's neighbourhood). Its cursor is a caret — whichever of the Terminal and the
Editor migrates first pulls the caret-and-selection shape, and the other reuses it. This decision
kept the measured overlap in place until migration, with no interim patch. Terminal has since
landed; current status belongs to the Workshop Goal Map, and the next-work order to VD-25.

### VD-26 — Intended outcomes and architectural fitness outrank local test agreement

**Status:** INCORPORATED (2026-09-10, founder in the Vision consolidation conversation)  
**Destinations:** `zen-orientation.md` §1 and §8; `executor-constitution.md` §a and rule 1;
repository AGENTS and affected routers; Workshop Goal Map §10

The founder distinguishes what code does from whether its cumulative result serves Zen. A phase
whose individual results pass but whose design makes later phases harder is not a good result.
The vision and selected direction govern that judgment; tests supply evidence of behavior.
An architectural-fit review comes before implementation and again before acceptance, considering
the whole arrangement and known next consumers. A conflict can require correcting code, tests,
or prose; no rule orders an automatic downward repair. Necessary future costs are explicit
decisions. This does not authorize speculative frameworks or ignoring required verification.

## 3. Seeded candidates — deliberately not promoted

### VS-01 — Flow may be a projection of earned semantic powers

**Status:** SEEDED  
**Raw source:** post-2026-08-18 architecture synthesis in `raw-vision-deltas.md`

Potential irreducible insight:

```text
fact/event -> value -> operator -> observation/request -> action/effect
                                         authority legitimizes the relevant doors
```

Flow should compose powers Zen independently owns; hot loading may teach it new powers. The
authored artifact should remain structured semantic logic with graphical and textual projections.

**Why not incorporated as roadmap work:** no current maker task requires a Flow representation, and
its exact persistence, scheduling, effect, and authority model is not yet earned.

### VS-02 — Outstanding obligations may deserve first-class legibility

**Status:** SEEDED  
**Raw source:** requests/obligations and potential-vs-outstanding-work synthesis

Potential irreducible insight: a door says work may arrive; an accepted request or schedule may
create work that is now owed; a resolution retires it. Conversation-scoped answer provenance is
already real, but a universal obligation lifecycle is not.

**Why not incorporated:** Timer, builds, asks, and handovers may share vocabulary without sharing
one correct mechanism. Wait for repeated live domains.

### VS-03 — Metadata can make a living system legible without becoming authority

**Status:** SEEDED  
**Raw source:** metadata/provenance/final-snapshot synthesis

Potential irreducible insight: facts may accrue under author/build/loader/runtime provenance, with
single-assignment keys and explicit JSON conversion. Metadata is inspectable evidence, never the
mechanism execution trusts. History, selected narrative, and a final standing snapshot complement
one another.

**Why not incorporated:** exact subject lifetime, custody, bounds, schema, and consumers remain
unearned. Current provider provenance is narrower and already owned elsewhere.

### VS-04 — Hot loading can become a maker feature

**Status:** SEEDED / LONG PATH  
**Raw source:** hot-loading and Builder responsibility synthesis; current EDIT-R1 future seam

Potential irreducible insight: a maker may identify a missing primitive, author the smallest native
power, let generated ceremony/building produce it, load it into the running catalog, and retain the
source/build/load intent so a fresh checkout can reproduce it.

**Why not incorporated as current work:** the same-shape rung is now built (VD-17): a rebuilt live
artifact reloads in place and the maker promotes it. The rest — authoring a missing primitive from
Workshop, generated ceremony producing it, and loading a NEW power into the running catalog — still
waits on the schema-builder / generated-boilerplate flow and on a concrete case.

### VS-05 — Two forms, one bridge

**Status:** SEEDED / HORIZON  
**Raw source:** `private/goals/two-forms.md`; the 2026-09-05 review of Zengine PR #10

A live interpreted form and a generated durable C++ form of one definition, bridged by Flow in both
directions: generation total and carrying its definition; deconstruction partial and improving,
using the Loom ABI's handles and drawing raw nodes for what it does not understand. "A raw node is
an operator iff it has no bus access, transitively" is the founder's hypothesis, not law.

**Why not incorporated as current work:** the founder chose the IDE road (VD-16). It is a
completeness test for seams the IDE loop touches, and the constraint of VS-01's neighbour holds:
let the C++ compiler parse C++.
