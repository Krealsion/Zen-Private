## 1. Rules

```text
ACT       current evidence supports a bounded near-term packet
WATCH     real pressure exists; more use should shape the answer
PARKED    real pressure exists but a named trigger has not fired
SEED      strategically useful candidate; not current product or architecture law
```

Pressure is not authorization. A known technical seam belongs in repository law; deliberately owed
but deferred work belongs in `private/backlog.md`.

### P-WORK-27 — Independent Info views leave three measured seams

**State:** WATCH; seams retained after founder acceptance and merge of #55 and its corrections
**Evidence:** [phase report](../reportbacks/zengine-independent-info-workbench-RB.md) and its evidence;
[corrections report](../reportbacks/zengine-independent-info-workbench-corrections-RB.md)

- **Responder identity is process-local.** A sample records the WeaveId Loom attests, which
  distinguishes a replacement only within one process. In the fresh-process run, the new
  `zengine.input` received the same id (#19) as the stored capture's earlier process. The notice
  therefore says an equal id may be an earlier process. It proves neither continuity nor change.
  The corrections met the same limit inside one process: a reload keeps the WeaveId and `Mail`
  exposes no sender incarnation, so Workshop's lease book cannot tell a reloaded Info from its
  predecessor. Info now ends its predecessor's leases when it activates (`PaneObservationEnded`
  with lease 0); another lease-holding provider would owe the same courtesy. A lease gates no
  send, so a leftover one is bookkeeping, not authority.
- **Invalidation reaches every accepting weave.** `InventoryChanged` is published to any weave
  that accepts it. Info now receives every change even while nothing is watched (eight per
  workbench story), and ignores the ones no watch needs. The cost grows with accepting weaves
  and change volume, not with watches.
- **Observation is Workshop-local and entry-only.** Leases live in Workshop's running image and
  cover linked Inventory entries only. Nothing watches a capture's original provider
  automatically; Sample is manual.

**Trigger:** a story needs cross-process source identity or automatic source watching, or
invalidation delivery becomes a measured cost as views and collections grow. Options include a
Loom-attested incarnation nonce, subscription-scoped invalidation, or a source-side watch
contract. The choice is the architect's, not an executor default.

### P-WORK-29 — A recipe authored in Files cannot name a toolchain

**State:** WATCH / MEASURED
**Evidence:** [tower defense report](../reportbacks/zengine-tower-defense-creation-story-RB.md),
evidence §9

`RecipeAuthorRequested` v2 has no toolchain field and the host composes the row, so a recipe Files
authors carries `toolchain_from: ""` and builds with CMake's machine default. Where that default is
NMake without an MSVC environment, the first build fails (`CMAKE_CXX_COMPILER not set`); the failed
configure then binds the workspace to that generator, so the next build fails again, and the
Builder has no clean action. The tower-defense example repairs both in every replay by typing
`toolchain_from` (the build tree Workshop came from) and a fresh `workspace` into the recipe.

**Trigger:** the next change to Files authoring or the Builder's single-source path, or a second
maker who hits it. Options: an authoring message that carries a toolchain (defaulting to the running
Workshop's own build tree where there is one), a Builder default for recipes that name none, and a
clean-workspace action. The message version and the default are founder decisions.

### P-LOOM-08 — A shape's name is first come on its host

**State:** PARKED — a solid approach, not now (the founder, 2026-10-05: preparing for the future)  
**Evidence:** #92's review, where the View Builder's and the Builder's states were both
`BuilderState` ([its follow-up](../prompts/whole-pixel-3-fixes.md), item 3); Loom's `ZEN_SHAPE`
(`include/zen/weave/shape.hpp`), [GATE-04](../Loom/docs/laws/admission-laws.md#gate-04--immutable-published-schemas)
and [the copied weave](../Loom/docs/guides/writing-a-weave.md).

`ZEN_SHAPE` names a shape by its bare C++ name, and a host's registry holds one definition per
`(name, version)` for as long as a participant that declared it lives
([LIFE-08](../Loom/docs/laws/lifecycle-laws.md#life-08--a-schema-is-retained-by-a-live-claim-never-by-having-been-registered)).
For one author that is the rule working: a shape changed without a new version is refused at load
when its old and new definitions meet, not at its first delivery
([ABI v9](../Loom/docs/decisions/declared-vocabulary-is-agreed-at-admission.md)). Between authors
it makes a coincidence a refusal, sometimes long after the fact: the two `BuilderState`s lived side
by side at v3 and v4 and would have collided once one version caught up with the other (the View
Builder's is `ViewBuilderState` from #92's follow-up).

One host per application keeps apart apps that never meet. It does not help a participant that
speaks two authors' vocabularies: an operator turning a music app's `Note` v1 into a notebook app's
`Note` v1 declares two definitions of one `(name, version)` and is refused in any host, its own
included -- and composing pieces is what Zen's operators are for.

The candidate is owned names: `music.Note` v1 beside `notebook.Note` v1, with GATE-04 unchanged
inside an owner. Loom already names its own shapes this way by hand (`zen.Activated`,
`zen.DispatchRefused`); the gap is the macro. A namespace declares its owner once, and every
`ZEN_SHAPE` inside it publishes under it:

```cpp
namespace music {
ZEN_VOCABULARY("music");  // every shape in this namespace is named under it
struct Note {
    std::int64_t pitch = 0, length = 0;
    ZEN_SHAPE(Note, 1, ZEN_FIELD(pitch), ZEN_FIELD(length)); // published as "music.Note" v1
};
}
```

An office-style owner (`zengine.workshop`) reuses a name already unique on a host. A later
capability layer could let only that office's holder define shapes under it, so a library could no
longer hold another author's name by claiming it first.

Not the answer: identity by content id alone (an author's slip becomes a silent split at its first
delivery, the failure ABI v9 removed); C++ namespaces (to Loom, `music::Note` and `notebook::Note`
are both `Note`); renaming every shape at once (a name is part of the content id, and a file that
names its shape, such as `"schema":"WorkshopKeymap"`, needs an authored migration). Adopt it for
new vocabularies, and for an old shape when it changes anyway.

**Trigger:** a participant must speak two authors' vocabularies, or two authors' libraries share
a host. [BL-WORK-35](backlog.md#bl-work-35--an-app-of-its-own-edited-live-from-workshop)'s link,
where an app admits Workshop as a guest, is the likely first.

## 7. Seeded strategic candidates — not current work

- **Flow as projection:** facts/events, values, operators, observations/requests, effects, and
  authority may form a maker-facing composition language. A graphical editor is one projection over
  authored semantic structure, not the sole representation.
- **Metadata as inspectable evidence:** identity/provenance facts may accumulate under clear
  claimant domains, but metadata must never become behavioral authority. A final living-system
  snapshot and History/Logger answer different questions.
- **Generated ceremony:** provider/schema/ABI/build glue may be generated while authored primitive
  code carries meaning. Let the C++ compiler parse C++; do not build an arbitrary-C++ parser.

- **Two forms bridged by Flow** (`private/goals/two-forms.md`, 2026-09-05): a live interpreted form
  (the paused `maker/` package is its runtime) and a generated durable C++ form, with Flow reading
  code into its world through the Loom ABI's handles and drawing raw nodes for what it does not
  understand — under the constraint above: let the C++ compiler parse C++. "A raw node is an
  operator iff it has no bus access, transitively" is the founder's hypothesis, not law.

- **Info rebuilt as a one-slot inspector** (the founder, 2026-10-02): a multi-pane weave rebuilt
  with today's Info as a quarry, rather than reshaped once more. Drop any element on it, or put it
  in a selection mode that boxes everything it can inspect and scans them as the pointer hovers;
  right-click any element to open an edit pane for it, as a context menu does. An edit pane is
  its fields with boxes and the actions the value allows (reset, save to live data where the
  value's owner supports it, save to Inventory), and drags out to whatever accepts it: a one-slot
  Inventory with editing built in. No list of panes, and no limit on source or destination. The
  selection mode is the UI-editing overlay's way in ([the goal map](goals/workshop.md)), so the
  two are one design. Ordered by the founder (2026-10-03) as BL-WORK-10 in `private/backlog.md`.

These candidates influence completeness tests only. They require their own current consumers and
authorized phases before they become architecture.
